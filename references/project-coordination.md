# 项目总控与执行会话

项目信息与风格足够明确后，先辨认各条内容的表达职责、共用资产和关联关系。强关联的视频可以属于同一组；独立条目保留自己的作品身份。是否有关联与是否需要并行分开判断，条目或会话的数量不决定声音政策。

工作方式优先在对话中对齐：内容与风格已明确、刚完成内容划分时，用一两句说明当前推荐，再问“这次在单会话逐条做，还是由总控安排分段会话并行做？”用户可直接用自然语言回答。回答后调用现有 `workspace` 的 `set_mode` 写入相同状态，随即继续对应制作；无需再到页面操作或重复确认。页面选中的明确方式与对话决定同等有效，已有决定直接沿用。初始数据中的 `single` 只是默认值，不凭默认值推定用户已经回答；明确要求留在当前会话或已选过方式时不再问。未作选择时继续可独立完成的规划，不把沉默当作同意创建会话。

默认推荐 `single`：当前会话可逐段完成整套制作，不为分段自动建会话。用户选择 `coordinated` 后，由项目总控统筹有关联的视频及独立条目。总控负责共用创意、作品之间的关系和共用资产；执行会话承担明确条目的完整制作。不要把已有项目强制改造成分布式流程。

## 进入协作模式

用当前可用的原生 Codex 会话工具完成操作，不建立自己的调度服务、后台轮询或第二套任务队列。工具名称和参数以当前实际 schema 为准。

1. 在项目登记中切换为 `coordinated`，调用 `set_thread_title` 把当前总控会话命名为“总控｜项目名”。只在拿到真实会话 ID 后登记 controller；名称本身不能证明会话已经创建。
2. 先用已有上下文及 `list_threads` / `read_thread` 寻找适用的执行会话。有现成会话就复用；确需新建时调用 `create_thread`。项目任务先 `list_projects` 获取真实项目标识，按返回的 Git 状态及用户已有目录约定选择环境，不虚构项目 ID、分支或目录。
3. 新建尚在准备时，返回的 clientThreadId 不是可调用的 threadId。未拿到正式 threadId 的条目保持待分配，不把准备中标为已开始执行。拿到正式 ID 后登记 thread_id 和必要的 host_id。
4. 用 `send_message_to_thread` 下发已经授权的范围。创建时已包含同一任务的初始 prompt，就不用重复发送一遍。用 `read_thread` 读取实际回报；需要等待时采用 `wait_threads` 的事件等待及游标，避免反复读取没有变化的状态。

会话工具不可用时，保留已有登记与明确缺口；能够在当前会话完成的工作继续按单会话方式进行，不以“协作已登记”冒充任务已经分发。

## 执行会话继承什么

执行会话必须读取同一份当前 `cinematic-storyboard/SKILL.md` 和本次阶段适用的参考，并完整执行该条目的制作工作：文字分镜、资产与分镜图、适用的那一次整段审查、生成建议、图像和视频提示词、参数与实际输入准备、所选平台上传、节点写入与回读，以及生成后的检查与返修。交接摘要是本次目标与真源索引，不能替代完整 Skill。

原提示词规范继续生效：开头写清声音与参考边界；正文让陌生模型独立理解；落实必要动作与摄影调度；普通参考图不变成逐幅必须到达的完整关键帧。项目总控不把执行会话缩成只绘图的工位。

总控只保存条目位置、会话归属、指令与实际回报，不复制孩子的完整 storyboard。共用资产直接引用实际采用路径，总控指定维护责任，执行会话不各自重建一份共用母图。变更接收范围按实际引用与内容关系判断，不能因为同属项目就无差别重做。条目内文字、素材有效性、审查事实与平台输入仍由各自制作真源维护。

## 共用要求修改后直接落实

将具体变更、依据和受影响条目登记为一条共用指令，再直接向这些条目的执行会话下发。用户已确认这种分工时，执行会话在原授权内落实并回报，不等待用户逐个进入催办。未受影响的独立作品与其他指令保持原状。

同步延续当前阶段与已有决定，不把文字或共用资产变更解释成重置阶段，也不重新启动已经完成的整段审查。仍须更新本次真正受影响的输入和生成建议；原图需要修订时如实标明，不把沿用制作权限当成素材仍然有效。

平台上传、写入提示词、回读与实际生成是不同动作。原本由用户点击生成的，仍由用户点击；没有新授权时，不因进入协作模式而增加付费生成、批量提交或其他外部动作。

发送成功只能登记 `sent`。只有读到执行会话关于当前版本的真实结果，且结果指向可核对文件、记录或平台回读，才登记 `applied`；遇到缺口登记 `blocked` 并说明原因。总控汇报要区分已下发、已落实和仍缺什么。

## 简短交接示例

下列是结构示例，替换成当前项目的实际路径、ID及决定后再发送，不逐字发送占位符：

> 执行条目：clip-b；作品：work-opening；关联组：产品开箱。你的表达职责是接续 clip-a 的打开盒盖的动作，同时让观众看清产品。制作目录：制作目录/clip-b。先读取当前 cinematic-storyboard/SKILL.md，并按适用阶段读取参考；继续执行完整制作，包括提示词与所选平台写入、上传及回读。  
> 共用指令 LOOK 第 2 版：采用已确认的冷色夜景，手部与包装布局沿用指定的正式资产路径。只同步 clip-b 受影响内容；目前仍是视频输入准备阶段，已完成整段审查不重做。声音与参考边界、陌生模型可独立理解的提示词规范继续有效。生成按钮仍由用户点击。  
> 请直接在已有授权内落实，回报指令 ID、版本、条目 ID、实际修改路径与平台回读结果；若有真实阻塞，说明缺项与已完成部分。

执行会话的简短回报应包含：`directive_id`、`version`、`item_id`、实际 `thread_id`、`status`、结果摘要、核对依据。回报不必粘贴完整分镜；给出真实位置和必要结论即可。

## 本地登记接口

登记放在 `doc.workspace.coordination`。`scripts/coordination.py` 只提供纯数据函数：`initial()`、`validate(state)`、`apply(state, command, now=None)`、`view(state, project_title='')`。调用者负责已有文档锁、修订冲突与持久化；模块不调用会话工具、不改变制作阶段、不新增作品声音规则。

- `set_mode`：`{op:"set_mode", mode:"single"|"coordinated"}`。
- `set_controller`：传 `controller:{thread_id,host_id?,title?}`；明确传 `null` 可清空登记。总控会话标题通过原生工具实际修改。
- `upsert_item`：传 `item:{id,title,work_id,group_id?,summary,directory,thread_id?,host_id?,status?}`。新条目默认 `planned`；状态可为 `planned/working/blocked/done`。更新只传需要变化的字段。已有 ID 不可改绑另一作品；没有会话 ID 就保持待分配。
- `upsert_directive`：传 `directive:{id,text,item_ids}`；可附 `expected_version` 防止旧版本覆盖。新指令版本为 1，正文变更递增；只增加接收条目不伪造新正文版本，已有相同版本的落实回报继续有效，新接收条目待落实。删除接收范围保留历史回报，但不再计入当前待办。
- `report`：传 `directive_id,item_id,version,thread_id,status,summary`；`applied` 还需非空 `evidence`，描述实际结果位置或回读依据。只接收当前指令版本和当前登记会话的回报；`sent` 不得覆盖已经收到的落实结果。

`view` 返回总控建议标题、条目、指令与当前落实状态。`pending_count` 是尚未落实的“指令 × 接收条目”数量，不是队列长度、失败次数或项目剩余视频数量。旧版回报保留为历史依据，不能显示成新版已落实；更换执行会话后同样等待新会话的真实回报。

这些操作由工作台的 `workspace` 接口统一持久化，完整调用形式见[工作台接口](workbench.md#工作安排参考请求与时长校准)。每次续做先读当前登记与待落实要求，再按原生会话工具的当前schema执行；无需用户逐个进入执行会话重述要求。
